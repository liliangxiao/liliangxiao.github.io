# Pain Points and Countermeasures in Hard Real-Time Firmware Design 固件硬实时设计的痛点与对策
**This article focuses on optimizing key scenarios under performance constraints, and does not completely replace or overturn existing real-time system designs. For non-critical or resource rich scenarios, we still use the traditional task-based theory. If we need to calculate the latest execution time, we need to consider the impact of critical scenarios on the latest execution time.
本文只针对性能紧张情况下的关键场景进行优化，不是完全取代颠覆现有实时系统设计。对于非关键且性能资源紧张的场景，我们仍然使用基于任务的传统理论，如果需要计算最晚执行时间，需要考虑关键场景的对最迟运行时间的影响。**
## Practical Dilemmas 实践中的困惑
### **Terminology Flaw (用语的偏差):**
The term "Real-Time System" is inherently misleading as it fails to capture a system's true deterministic characteristics. To eliminate this ambiguity, this article proposes the term **"Timely Reaction System (TRS)"**. “实时系统”的用语本身存在名称缺陷，不能反映其准确特征。本文采用**“及时反应系统” (Timely Reaction System, TRS)** 进行取代，以避免理解误解。
### **Fundamental Flaws in Existing Theories (现有的实时理论根基缺陷):**

The prevailing theoretical foundation relies on Rate Monotonic Scheduling (RMS) or Deadline Monotonic Scheduling (DMS) and priority-based task preemption. This approach suffers from inherent defects when facing real-world engineering limits:

最普遍采用的理论（如 RMS 或 DMS 和基于优先级的任务抢占）在面对真实的工程极限时，存在天生的缺陷：

- **The Illusion of Abundant Resources (算力充足的伪命题):** RMS and DMS are essentially determinism-guarantee theories built on the false assumption of abundant computational resources. However, constrained by SWaP-C (Size, Weight, Power, and Cost) and high-frequency physical requirements, hard real-time systems inherently operate on the edge of resource scarcity. These theories lack degradation mechanisms and cannot adequately handle situations with constrained or exhausted resources. 传统理论本质上是基于“算力资源充足”前提的确定性时间保障理论。然而，受限于 SWaP-C（尺寸/功耗/成本）铁律与物理系统内卷的高频响需求，硬实时系统往往天生处于资源紧缺的边界，传统理论根本无法很好地应对瞬时资源紧张或过载的情况。
    
- **Confusing Urgency with Criticality (混淆“紧迫性”与“重要性”):** Under extreme conditions (resource exhaustion), these scheduling algorithms blindly prioritize tasks based on mathematical metrics (shortest period or deadline) rather than the actual physical consequences of failure. They fail to differentiate between "urgent but trivial" and "critical and fatal." 在极限工况（资源枯竭）下，现有调度算法盲目依据数学周期或时限进行调度，无法区分“紧急但不重要”和“核心且致命”的场景。
    
While existing theories can implement basic real-time features under rich resources, **this fundamental disconnect from actual operational scenario values degrades timeliness, often sacrificing high-value core scenarios to schedule trivial tasks. This causes systems to falter under extreme edge cases and forces engineers into endless, reactive optimization cycles.** 虽然现有理论在算力充沛时能实现实时功能，但**这种与实际物理场景价值的脱节，常常导致过载时产生“保芝麻丢西瓜”的反向调度。这使得系统在极限工况下力不从心，并给固件工程师带来海量的被动优化工作量。**
### **Blind Spots in Current Methodology (现有实时设计方法盲区):**
Conventional real-time design predominantly focuses on the software layer, neglecting holistic system attributes. This narrow scope prevents firmware engineers from fully grasping the underlying system architecture. 现有实时设计方法往往仅关注软件层面，忽略了实时设计的系统属性，导致固件工程师难以全面掌握系统底层架构。
Addressing these pain points, this article introduces an architectural framework based on **Scenario-Level Absolute Priority Preemption**. It aims to inspire the design of TRS while providing actionable diagnostic clues for current hard real-time development. 本文针对现存痛点，提供一套基于**场景级别的绝对优先级抢占**的系统设计思路。一方面为 TRS 的设计提供思路，一方面为当前硬实时系统的开发提供问题解决线索。

## I. From "Task Preemption" to "Full Scenario Preemption"
**从追求“任务抢占调度”到追求“场景的绝对完全抢占”**
### **The GAP between General-Purpose RTOS Design and Engineering Practice**
**通用 RTOS 设计与工程实践的间隙**
Most RTOS implementations center on task/process scheduling. In engineering practice, this focus deviates from the ultimate goal: **guaranteeing critical deadline scenarios**. When pushed to the limit, engineers are forced to endlessly tune tasks and interrupts to squeeze out performance, consuming time and compromising reliability. 所有 RTOS 实现均以任务或进程调度为核心，这在工程实践中与“保障关键时限场景”的目标不符。这导致工程师在接近极限的情况下不得不反复优化任务和中断，既耗时又埋下软件可靠性隐患。
### **Full Monopoly of Resources for the key scenarios is a must in extream conditions**
**关键场景在极限情况下必须独占资源**


Under extreme conditions, guaranteeing a **Critical Timely Scenario** requires it to preempt and strictly monopolize all necessary hardware resources. Performance can be reclaimed by eliminating three specific overheads: 在极限情况下，要保障**关键时限场景**，该场景必须抢占并独占所有硬件资源。通过消除以下三项开销，可以找回流失的性能：
1. **Interrupt Overhead (中断开销):** Interrupts can unpredictably hijack resources. By physically masking irrelevant interrupts during a Critical Timely Scenario, the system guarantees absolute resource monopoly. **Crucially, interrupts within the scenario must also be subject to strict frequency control, permitted only when essential to avoid resource waste.** 中断会占用硬件资源。通过屏蔽场景无关的中断，保障**关键时限场景**的资源独占。**同时，场景内的中断也必须进行频率管控，只在必要时允许触发，避免资源浪费。**
It should be noted that the impact of disabling interrupts (e.g Watchdog) must be taken into account and **properly addressed**. Please also refer to Point 4.
需要注意的是，关闭关键场景相关的中断(比如看门狗定时器)的**影响需要考虑和对应**，同时请看第4点。

2. **Priority Inversion by Minor Scenarios (次要场景的任务干扰):** Existing theories (like RMS) prioritize tasks with shorter periods, which clashes with scenario-based urgency. Under extreme loads, short-cycle, low-value tasks can cause critical scenarios to miss deadlines. **Scenario-based priority** ensures high-priority scenarios receive ultimate protection during worst-case execution time (WCET). 现有理论（如 RMS）要求执行周期越短优先级越高，这与基于场景的优先级冲突。在极限负载下，短周期但低价值的任务会造成**关键时限场景**失效。通过基于场景的优先级保障，最高优先级场景可获极限护航。
3. **Scheduling Overhead (调度消耗):** Context switching consumes CPU cycles. 
- By serially executing tasks within a scenario in a deterministic sequence(Tasks within a real-time scenario should be serial; essentially, they can be merged into a single execution flow. The reason we decompose them into discrete "tasks" is primarily to facilitate the sharing and reuse of these functional units across different scenarios.), the system completely bypasses internal scheduling overhead. 基于任务的切换本身消耗资源。通过对场景任务进行有序串联（实时场景的任务应当是串行的，也就是说是可以合并为一个任务的。分解为任务是方便任务在场景之间的共享），可以节省掉任务调度的资源消耗。

- The scheduling is prefered to be interrupt-triggered, and timed scheduling can be performed with nS or uS precision by triggering timer interrupts. Unlike normal task with normally runs at period over 1ms, deadline critical scenarios can run at period at uS level.
调度倾向为中断触发，通过定时器中断触发可以在nS或者uS级精度进行定时调度。不同与常规任务的ms级运行周期，时限关键场景的运行周期为uS级。

4. **Use redundancy for Smoothness of minor scnarios 使用性能冗余为次要场景提供平滑保障**
 Once the critical scenario is guaranteed, remaining "Slack Time" can be used for other interrupts. Moreover, communication between these interrupts and minor scenarios must use **flow control or buffering** to absorb the jitter introduced by high-priority preemption. **When redundancy is enough, current RTOS theory can actually also work well. But senario based preemption helps you tune deal also with situations where redundancy is not enough**. 在保障关键场景后，利用剩余时间（Slack Time）允许次要中断执行。同时，中断与次要场景的通信需引入流控或缓冲，以吸收高优先级抢占带来的抖动，且绝不可透支主场景的资源冗余。**在冗余足够的情况下，现有RTOS理论可以很好适应，但是基于场景优先级剥夺思路可以帮助在资源不足时进行调整达到最佳性能**。

## II. Architecture-Level Reliability Guarantee
**二、 架构级的可靠性保障**
-  Scenario-based Isolation (Module Partitions) 基于场景的隔离 (模块分区) 
	- **Isolation of software modules is implemented based on scenario**. 基于场景进行模块隔离。
	- Memory isolation is achieved by the **MPU**.通过 MPU 实现内存隔离。
	- Communication between partitions is **asynchronous**; for **time-critical communication**, data flow is restricted to the **one-way direction from high-priority to low-priority** partitions.分区间采用**异步**通信方式；针对实时响应类通信，数据仅允许从高优先级分区向低优先级分区**单向**流动。
	- High-priority scenarios may read outputs from low-priority ones, while such communication **shall not trigger time-critical responses** and does not constitute a TRS inverted partition dependency. 高优先级场景可读取低优先级场景的输出，此类通信**不得触发高优场景的及时响应**，因此不构成TRS分区依赖关系倒置。
	This is a critical concept as a critical deadline scenario can rely on non-critical low layer tasks, in this case, the non-critical low layer tasks do not need to be inlucded the the critical deadline scenario as the input does not trigger time-critical response.这是一个关键概念，因为高优场景可以依赖于非时限宽松的底层任务，在这种情况下，时限宽松底层任务不需要包含在高优先场景中, 因为输入不触发高优先场景的及时响应。
	- All partitions **run independently, and in case of memory access conflicts, **only the affected single partition needs to be restarted**. 各分区独立运行，若发生内存访问冲突，仅重启受影响的单个分区即可.
- **Fast Automatic Recovery (快速自动恢复):** The system must possess lightning-fast recovery capabilities, ensuring that any fault recovery never disrupts a Critical Timely Scenario. This "seamless self-healing" requires native recovery mechanisms and **Default-Value Fallback** for cross-scenario messaging. 系统应具备极速自愈能力，确保故障恢复过程不会延误**关键时限场景**。底层架构必须提供原生的自动恢复机制与默认值回退能力。
- **Message Record & Replay Mechanism (消息记录与重放)**: The architecture should support efficient inter-scenario message recording. When intermittent bugs occur, developers can inject historical message streams to precisely replay the failure, instantly reproducing the "crime scene" for rapid resolution. 架构应支持高效的跨场景消息记录与重放。一旦出现偶发 Bug，可通过注入历史消息流精确重放，瞬间还原“案发现场”以快速除错。

## III. System-Level Performance Solutions
**三、 系统级性能解决方案**
If software optimization hits a physical ceiling, system-level hardware adjustments are required: 如果软件优化后仍无法达标，说明触及了物理天花板，需要进行硬件升级或调整：
- **Hardware Adaption (硬件适配):** Use dual-core MPUs, DSPs for algorithmic acceleration, or FPGAs/ASICs to overcome bus and computational bottlenecks. 寻找性能瓶颈，利用双核 MPU、DSP 加速算法，或使用 FPGA/ASIC 解决总线瓶颈。
- **Load Balancing (负载均衡):** In multi-core architectures, Critical Timely Scenario loads should be distributed evenly across cores to prevent single-core congestion. 在多核架构下，**关键时限场景**的负载应尽量平均分配到每个核上，避免单核拥堵。


Finally, it should be clarified that most scenarios are not core Timely Reaction System (TRS) scenarios, such as those requiring second-level response. When hardware performance meets their worst-case execution requirements, there is no need for TRS rigid design, and scheduling can be more flexible (as long as it does not interfere with core TRS resources).
最后需明确，绝大多数场景不属于核心及时响应场景（TRS），如秒级响应需求场景。当硬件性能覆盖其最坏工况执行需求时，无需按TRS强规设计，调度可更灵活（不干扰核心TRS资源即可）。
