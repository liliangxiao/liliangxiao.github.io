# Scenario-Based RTOS Optimization (SBRO): An Engineering-Oriented Enhancement for Hard Real-Time Firmware

**Author:** Liangxiao Li

### Abstract

This article proposes the Scenario-Based RTOS Optimization (SBRO) architecture as an engineering-oriented complement to traditional task-based scheduling. Rather than replacing existing real-time theories, SBRO introduces a scenario-aware layer that dynamically clusters and prioritizes related tasks to manage critical performance bottlenecks. This approach provides a practical framework for ensuring the deterministic execution of high-value physical scenarios under resource scarcity, while maintaining formal mathematical compatibility with standard Rate Monotonic Scheduling (RMS) frameworks.

### 1. Introduction

According to Stankovic (1988), the correctness of a real-time system depends not only on the logical result but also on the time at which the result is produced. Traditional scheduling theories, such as RMS and Deadline Monotonic Scheduling (DMS) (Liu & Layland, 1973), effectively manage concurrency by treating tasks as independent entities. However, under extreme resource constraints, this mathematical abstraction often diverges from physical engineering requirements, leading to unacceptable jitter.

To bridge this gap, we propose the Scenario-Based RTOS Optimization (SBRO) framework. SBRO shifts the scheduling paradigm from managing isolated tasks to managing unified "scenarios"—clusters of interdependent tasks that must execute as a single deterministic block to fulfill critical physical contracts.

### 2. The Engineering Context of SBRO

Traditional RTOS extensions often bypass the scheduler entirely, violating system modularity and risking priority inversion. SBRO complements traditional scheduling by specifically addressing "Critical Scenarios"—situations demanding deeply optimized execution without destroying the underlying RTOS structure.

While Mixed-Criticality Systems (MCS) (Vestal, 2007) manage resource scarcity by dynamically dropping lower-criticality tasks under pessimistic execution conditions, SBRO takes a different structural approach. Rather than relying on dynamic preemption, SBRO bypasses context-switching overhead entirely by clustering critical tasks into an atomic, interrupt-masked sequential block. SBRO acknowledges that while an RTOS effectively manages the majority of background system tasks, critical physical control loops require a distinct management layer that recognizes the *context* of the tasks to guarantee Worst-Case Execution Time (WCET).

### 3. The SBRO Methodology

The SBRO framework integrates with existing systems via a Scenario-Based Layer that activates only when predefined physical or temporal conditions are met. The optimization relies on three core mechanisms:

* **Same-Frequency Task Clustering:** Tasks within a defined SBRO scenario must share identical execution frequencies. This ensures the scenario operates as a unified, deterministic control loop rather than a loose collection of threads.
* **Unified Priority & Sequential Execution:** Upon scenario activation, clustered tasks are elevated to the highest system priority and executed sequentially. This structurally bypasses intra-scenario context-switching overhead.
* **Interrupt Masking for Jitter Control:** To eliminate external execution jitter during a critical scenario, SBRO applies selective interrupt masking. This converts random preemptive delays into a predictable, mathematically bounded system bias.

### 4. Architecture and Reliability

To ensure safe integration with standard RTOS designs, the SBRO architecture mandates strict operational boundaries:

* **Pre-emptive MPU Isolation:** Memory boundaries between scenarios and background tasks are enforced via a Memory Protection Unit (MPU). To prevent MPU reconfiguration from adding overhead *during* the critical loop, boundary configurations are loaded pre-emptively during the scenario's initialization phase.
* **Asynchronous Communication:** Data and control signals may flow bidirectionally between high-priority SBRO scenarios and low-priority background tasks. However, to definitively prevent priority inversion and preserve WCET, any communication flowing from low-priority tasks up to the high-priority SBRO scenario must be strictly non-blocking. By utilizing lock-free data structures or asynchronous buffers, the critical SBRO layer can poll for necessary background data without ever waiting on a lower-priority process.
* **Strict Execution Time Bounding (Sub-Millisecond):** Because SBRO relies on temporary interrupt masking, the framework dictates that any critical scenario must have a mathematically proven WCET of strictly less than the RTOS SysTick period (typically < 1ms). By enforcing this sub-millisecond constraint, the SBRO scenario may temporarily delay a scheduler tick, but the pending interrupt is immediately serviced upon exiting the scenario. This guarantees that the RTOS scheduler seamlessly catches up without requiring complex, overhead-heavy state recovery mechanisms.

### 5. Formal Schedulability Impact

Because the SBRO methodology temporarily unifies tasks, elevates priority, and masks interrupts, it introduces a blocking factor to the rest of the system. However, this remains compatible with standard Rate Monotonic Scheduling (RMS) by treating the maximum execution time of an SBRO scenario as a predictable blocking time ($B_i$).

System designers can validate background task schedulability using the extended RMS utilization bound:

$U = \sum_{i=1}^{n} \frac{C_i}{T_i} + \frac{B_i}{T_i} \leq n(2^{1/n}-1)$

Where $C_i$ is the computation time, $T_i$ is the period, and $B_i$ represents the Worst-Case Execution Time of the highest-priority SBRO scenario that can preempt or block task $i$. By bounding the scenario time, SBRO converts unpredictable jitter into a verifiable mathematical constant.

### 6. Conclusion

Scenario-Based RTOS Optimization (SBRO) provides a vital engineering enhancement to traditional real-time scheduling. By introducing a scenario-aware layer, it enables systems to handle extreme performance bottlenecks while retaining the architectural flexibility of established RTOS models. It does not replace traditional theory; instead, it provides the deterministic safeguard required for core physical operations, ensuring that the most critical system contracts are fulfilled even under the most demanding constraints.
